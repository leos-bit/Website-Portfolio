Overview

NEXA stands for Network of Experts and Agents. The research asks how compact, specialized AI systems can support manufacturing process design and monitoring without losing the provenance, structure, and technical constraints contained in the source material. My work has focused on the data and runtime infrastructure that makes that possible: extracting reliable records from difficult documents, preserving evidence and metadata, and making the resulting knowledge usable by troubleshooting tools.

The public repository now contains several connected systems rather than one monolithic model. Native PDFs use a fast PyMuPDF route; scanned or sparse pages can be routed through Surya or NVIDIA Nemotron OCR v2; operator notes and handwritten PVD forms have dedicated, form-aware pipelines; and the troubleshooting layer combines structured source ingestion, retrieval, schemas, and a FastAPI service.

Technical Document Ingestion

Manufacturing references mix clean digital text with scans, tables, equations, figures, safety notes, and repeated front matter. I improved the OCR/VLM path so extraction quality is measured at the page and chunk levels rather than treated as a single OCR score. The pipeline retains reading order and provenance, routes native pages away from unnecessary GPU OCR, preserves short structured table rows, and produces readable JSONL plus metadata and optional Parquet exports for downstream dataset assembly.

  • Added database-safe cleanup and paragraph exports while preserving technical content and source location.
  • Integrated a persistent Nemotron worker and adaptive batching so multiple documents can reuse a warm OCR model.
  • Added bulk ingestion, resume behavior, per-document manifests, coverage metrics, semantic deduplication, and asynchronous VLM enrichment.
  • Improved caption routing, sparse-table retention, interlock-row preservation, and missing-page detection with regression tests.

Manufacturing Troubleshooting Stack

I built the initial troubleshooting retrieval and API scaffold, then expanded it to ingest multiple source types and support remote evaluation. This work introduced typed maintenance-event and knowledge schemas, retrieval over manuals and service records, source-selection tooling, a troubleshooting copilot layer, and a FastAPI boundary with tests and local pgvector validation support.

  • Created retrieval, knowledge models, SQL schemas, representative maintenance events, and troubleshooting cases.
  • Added source ingestion for multiple technical record types and selection of preferred chunks.
  • Expanded API tests and remote-ready command-line tooling for repeatable case evaluation.
  • Kept source evidence and recommended review actions available to downstream troubleshooting logic.

Handwritten PVD Log Reconstruction

Scanned production forms are a different problem from ordinary PDF OCR, so I developed a dedicated pipeline for reconstructing PVD75 logs. It separates form structure from handwriting, extracts bounded field regions, records confidence and raw predictions, and exports fixed-form text, CSV, and metadata instead of flattening each page into an untraceable transcript.

The later commits added page-grouped training manifests, TrOCR tuning, registered scanner test sets, field-specific run-number and date recognizers, candidate retries, temporal sequence checks, recipe priors, contact sheets, and reconstruction metrics. Experimental specialist checkpoints remain behind explicit quality gates when held-out accuracy is insufficient, which keeps uncertain model output from silently becoming manufacturing data.
