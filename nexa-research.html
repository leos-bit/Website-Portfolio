Overview

NEXA stands for Network of Experts and Agents. The core idea is to use smaller, more efficient language models as specialized technical experts and runtime agents instead of relying on one large general-purpose model. In the slide deck, the system is framed as a unified path from user objectives to validated process design decisions, with policy constraints, retrieval, fine-tuning, prompt optimization, and runtime feedback all working together.

The project has now grown beyond the earlier TurboOCR comparison branch into a broader manufacturing AI platform. The current work spans native-plus-OCR PDF ingestion, page-level metadata contracts, handwritten equipment-log reconstruction, grounded Q/A/context generation, diagnostic reasoning over service incidents, and a runtime RAG layer that can be served directly into OpenWebUI as an OpenAI-compatible model endpoint.

Repositories: GitHub main branch and the local OpenWebUI-connected workspace in /Users/leoshaw/Documents/VSCode/nexa.ai.

Research Architecture

The workflow combines document routing, native and OCR extraction, chunk-quality scoring, and a layered expert-agent runtime with validation and post-run review before knowledge is exposed to downstream tools.

Current System Architecture

The repository is now organized around several connected layers. The OCR and VLM pipelines extract structured technical content from manuals and references, the handwritten pipeline reconstructs equipment logs into tabular records, and the grounded reasoning pipeline turns accepted source material into cited Q/A/context data for both training and runtime retrieval.

  • nemotron_ocr_vlm_pipeline/ is now the main research-compliance OCR path, keeping PyMuPDF native fast-path extraction while routing harder pages through Nemotron OCR v2.
  • handwritten_log_pipeline/ reconstructs scanned PVD75 handwritten run logs into form-aware CSV and JSON outputs with bounded retries and field validation.
  • slm_reasoning_pipeline/ builds grounded Q/A/context tuples, diagnostic datasets, normalized Q/A/C stores, and runtime RAG answers with exact supporting quotes.
  • openwebui_api.py exposes that runtime RAG stack as an OpenAI-compatible service so OpenWebUI can talk to the manufacturing assistant directly.
  • eval_tools/, regression suites, and schema validators keep the data, retrieval behavior, and grounded-answer quality inspectable instead of opaque.

Document Ingestion And Knowledge Extraction

The manufacturing setting is full of mixed-format source material: clean native PDFs, scanned pages, figures, tables, equations, front matter, and handwritten operator logs. The newer NEXA work treats ingestion as a systems problem rather than just an OCR problem. Pages are routed between native extraction and OCR, readable JSONL and metadata sidecars preserve provenance, semantic deduplication tracks repeated content, and bulk ingestion keeps large document sets structured enough for downstream reasoning and retrieval.

Grounded Reasoning Pipeline

A major new piece of work is the grounded SLM reasoning pipeline. Instead of jumping directly from OCR text to a chat model, the system first builds readable Q/A/context artifacts, audits them, and then loads accepted rows into a normalized store. Runtime RAG uses keyword-indexed lookup plus cited Laguna synthesis, exact-quote verification, and fail-closed abstention when evidence is weak or mismatched.

  • Offline tuple generation turns accepted source chunks into deterministic Q/A/context rows with metadata sidecars for inspection.
  • Curated Q/A/C stores deduplicate repeated context text while keeping provenance, keyword lookup, and optional relation layers visible.
  • Diagnostic generation supports symptom-to-cause reasoning with ranked hypotheses, applicability conditions, evidence quotes, and discriminating next checks.
  • Runtime RAG audits exact source quotes and numeric claims before returning an answer, rather than trusting model output on its own.

Current Research Direction

The project is now less about a single OCR backend and more about end-to-end grounded manufacturing AI. The current focus is on keeping ingestion fast and structured enough for real datasets, improving handwritten-log recovery, strengthening diagnostic retrieval and audit behavior, and making the OpenWebUI path reliable enough for interactive technical support without giving up traceability or exact-source grounding.
